从 Development 到 Live：研究证据为什么不能越级授权

Last materially modified: 2026-08-29

TL;DR：一个好看的回测数字，不是一张可以层层通用的通行证

NarrowGate 的 Full-Multiscale 研究在 BUY 侧得到过一个很容易令人兴奋的数字：高阶 Boolean 候选 E3_HIGHER_ORDER_BOOLEAN 相对实验冻结时的 exact owner baseline，campaign-terminal value 的点估计改善了 +0.458577 USDC/day。但这个数字没有授权 final refit，没有授权读取 Validation，没有授权打开 sealed holdout，更没有授权 action、canary 或 live。

原因并不神秘：研究证据不是“有或没有”两档，而是一条逐级收窄不确定性的权限链。Development（开发集）回答“学习流程是否产生了值得继续检验的候选”；final refit 回答“最终要检验的是哪一个固定 artifact”；Validation（验证集）回答“固定候选能否在未参与发现的数据上复现”；sealed holdout（封存留出集）只用于最后一次独立检验；action 与 live 则还要经过执行、安全和 owner 决策。前一级没有通过，后一级不会自动存在。

这篇文章只解释研究证据与权限的关系，不讨论任何当前 live 状态，也不建议真实交易。Full-Multiscale 的公开证据止于 30 日 historical Development 的 nested chronological out-of-fold（嵌套时间序列样本外）结果；精确 OOF 行、cache 与 owner-side artifact 位于 private evidence store; not distributed with the public repository。

这是 Full-Multiscale 总览 的证据治理篇。

1. 先把“证据”和“权限”分开

一份报告可以证明某件事发生过，却不一定允许下一件事发生。比如，一次 Development replay 可以证明“某个学习流程在 20 个 outer-test days 上得到正点估计”，但它不能证明“最终固定规则在新日期上仍然有效”，更不能证明“真实交易系统应当执行这条规则”。

可以把第 $k$ 级已经获得的证据写成 $E_k$，该级预先冻结的通过条件写成 $G_k(E_k)$，第 $k$ 级权限写成 $A_k$。晋级不是看研究者是否喜欢结果，而是一个单向递推：

这里的“权限”也不是法律概念，而是可审计的研究状态：当前材料究竟只允许继续做方法开发，还是已经允许读取下一块数据、固定 artifact、登记 action，乃至进入独立的运维决策。

2. 七级阶梯分别回答七个不同问题

图 1：Full-Multiscale 到达 historical Development OOF 后在门槛处停止；右侧灰色阶段没有被这项研究创建。

层级 它真正回答的问题 它不能证明什么
0. Design / preregistration 问题、样本、baseline、候选、fold、estimand 和统计门槛是否在看结果前固定？ 不证明候选有效
1. Development OOF 学习算法只用过去数据时，能否产生稳定且满足硬门槛的候选？ 不证明存在一个已经固定的最终 artifact
2. Final refit 用完整 Development 按原算法重训后，最终规则、特征和动作是否唯一固定？ 不证明它在新数据上复现
3. Validation 固定 artifact 能否在未参与 discovery 的日期上通过预先规定的门槛？ 不等于最终独立确认，也不等于部署许可
4. Sealed holdout 最后一次封存证据是否支持同一固定结论？ 不证明实时系统、延迟和交易安全
5. Research-supported action 研究是否足以登记一个明确、可执行的 action identity？ 不替代 owner 的风险与资本决定
6. Canary / live decision 独立运维流程是否接受代码、配置、回滚、资源和交易风险？ 不能反过来改写研究门槛已经通过

表中最容易混淆的是第 1 与第 2 级。Development OOF 评价的是“在不同历史时点，学习算法会产出怎样的 fold-specific policy”；final refit 才会用完整 Development 生成一个以后不再修改的具体 artifact。前者通过，也不意味着后者已经自动生成。

Full-Multiscale 的 BUY E3 正好展示了区别。它的 gross terminal uplift 点估计是 +0.458577 USDC/day，四个 outer fold 都为正，20 个测试日中 13 日为正，fill retention 为 97.29%；但是 primary day-level simultaneous interval 是 [-0.348400,+1.265554] USDC/day，仍跨过零。它相对 action-matched control 的 semantic increment 点估计为 +0.193888 USDC/day，对应的 day interval [-0.715169,+1.102945] 也跨零。再加上冻结 hierarchy 第一层和 tail/lifecycle gates 失败，Development 的晋级条件整体为假。

这张图把“结果”和“权限”放在同一条阅读路径上：先问绝对经济值，再问相对差异，再问不确定区间，最后才问允许进入哪一级。只展示绿色的相对点估计，会把中间两道证据门从读者视野里删掉。

4. 为什么不能失败以后直接读 Validation

Validation 的价值来自它没有参与候选选择。若研究者在 Development 失败后打开 Validation，再根据那里的结果改 feature、门槛、duration 或聚类方法，Validation 就加入了 discovery chain，不再是原来声称的未见证据。

并且候选映射 $\pi^*$ 在读取 $\mathcal D_{\mathrm{next}}$ 之前已经固定：

如果 Development 没有产生被合同支持的 $\pi^*$，那就没有东西可以合法送入 Validation。此时“先看看 Validation 再决定”不是多拿一份信息，而是在消耗验证集来继续调参。

sealed holdout 的要求更严格。它不是第二个 Development，也不是在 Validation 不理想时的复活机会。只有一个已在 Development 和 Validation 连续通过、且身份没有变化的候选，才有理由进行一次性 unseal。

5. 一个轴是统计证据，另一个轴是执行真实性

即使统计晋级链完整，证据时钟和回放机制仍决定它能授权到哪里。Full-Multiscale 使用的是 exchange-time、modeled queue，并对没有共同 sequence 的同毫秒 trade/book 歧义做 censor。它可以回答这个冻结 replay identity 下的动作价值问题，却不拥有 strict exchange-queue truth、receive-time transport parity 或 exact live lifecycle authority。

可以把证据看成两个互相独立的坐标：

“通过 sealed holdout”只提高第一个坐标；“native sequence 完整”或“receive-time 可复现”提高第二个坐标。任何一边较弱，都不能由另一边补偿。一个 modeled replay 的漂亮区间不会自动变成实时队列证明；一个严格复现代码路径的 parity test，也不会自动证明策略有经济 uplift。

这就是为什么公共报告需要同时写清：样本属于 Development、时钟是什么、queue identity 是什么、哪些歧义被 censor、哪些 artifact 未公开、以及当前结果没有哪些 permission。只写“回测赚钱”把这几个维度压成一句话，读者就无法判断结论实际覆盖到哪里。

6. Owner decision 与研究结论也不是同一层

现实系统可能因为风险偏好、资本预算、可逆性或业务约束做出一个 owner operational decision。这种决定可以显式接受研究尚未消除的风险，但它不能倒写历史，让一个没有通过的 Development gate 变成“其实已经验证”。

反过来也一样：一个研究支持的 action 并不要求 owner 必须上线。研究回答“在冻结合同下是否有足够证据”；owner 决策还要回答“现在是否值得承担工程、市场、资本和回滚风险”。

所以需要保留两条独立记录：

research chain: design -> Development -> refit -> Validation -> holdout -> supported action
operations chain: candidate release -> safety gate -> canary -> observation -> promotion/rollback

它们可以引用同一个 artifact identity，但不能互相替代。运维成功不能补研究区间，研究显著也不能补启动、撤单、仓位、资源或回滚证明。

7. Full-Multiscale 实际停在了哪里

本研究已完成的是：冻结 30 个 family-specific historical Development dates，在四个 expanding outer folds 上产生 20 个 untouched outer-test days，用 nested chronological discovery 学习 fold-specific policy，再对 candidate 与 exact B0 分别执行 repeated sequential full-path replay。

本研究没有获得的是：supported side、最终固定规则、final refit、Validation admission、sealed-holdout access、research-supported action 或 live authority。形式化地说：

这是一项完成的阴性研究，而不是“还差一步的上线候选”。它保留了 BUY E3 作为值得未来重新确认的 hypothesis，但未来确认必须在新证据读取前重新冻结 artifact 与统计合同，并建立新的 confirmation identity；不能继续在已经消费的 30 日上挑区间、改 hierarchy 或缩小搜索空间后宣称独立复现。

8. 读一份策略报告时，可以问这八个问题

  1. 这份数据属于 Development、Validation 还是 sealed holdout？
  2. feature、action、baseline、fold、estimand 和门槛是在看结果前固定的吗？
  3. 报告评价的是学习算法的 OOF 表现，还是一个最终固定 artifact？
  4. 点估计之外，预注册的区间、support、tail 与 lifecycle gates 是否全部通过？
  5. BUY 与 SELL 是否分别报告，还是被 pooled 数字掩盖？
  6. replay 是 modeled queue、strict native，还是 receive-time/exact lifecycle 证据？
  7. 当前材料明确授予了哪一级 permission，又明确拒绝了哪一级？
  8. owner 运维决定是否被错误包装成 research confirmation？

只要其中一个问题答不清，“这个策略能不能上线”就问得太早。先把它能证明什么、不能证明什么说清楚，往往比继续增加一张收益图更有价值。

9. 公开证据

  • Full-Multiscale prospective design：原始问题、candidate ladder 与阶段权限设计。
  • Offline successor Spec：30 日 Development、nested OOF、source gate 与 modeled-queue 证据边界。
  • Formal Development component report：BUY/SELL 聚合结果、hard-gate failure 与最终决定。
  • Public machine receipt：结构化的 evidence stage、permissions 与结果摘要。
  • Handoff completion audit：区分已完成的 Development 与未获得的 final-artifact/confirmation 权限。

结语：最可靠的研究，不只会给结论，也会拒绝越权

证据阶梯的价值，不是把研究流程变得官僚，而是让每个数字只承担它真正能承担的证明责任。Development 的正点估计可以生成 hypothesis；稳定的硬门结果才允许 refit；固定 artifact 才能进入 Validation；Validation 通过才有资格触碰 sealed holdout；即使研究链全部通过，action 与 live 仍有独立的安全和 owner 权限。

Full-Multiscale 最值得保留的结论因此不是“BUY E3 看起来不错”，而是：它在该停下来的位置停下来了。没有用 week-level 的有利区间覆盖 primary day-level failure，没有让后层 winner 绕过 feature hierarchy，也没有把一次 owner 决定冒充研究确认。

一套能够明确说“到这里为止”的研究系统，才有资格在未来某次真正通过时说“现在可以进入下一层”。
