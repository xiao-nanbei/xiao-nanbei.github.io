研究版本还是执行失败？从 formal-v13 到 formal-v27 的身份治理

Last materially modified: 2026-08-29

TL;DR：模型没变、问题没变，就不要用版本号伪装一次修复

问题：Full-Multiscale 的历史记录里出现了 formal-v13 到 formal-v27。这是否意味着研究连续迭代了十五代，或者看了十五次经济结果以后不断调模型？

结论：不是。这些名称是历史 execution-attempt aliases，也就是执行尝试别名。只要冻结的样本、baseline 与 candidate ladder、时间折叠、estimand 和 statistical contract 没变，scheduler、cache、C++ lockstep、mmap lifetime、resume 或 serialization 的修复都只产生新的执行尝试，不产生新的 research identity。

证据边界：本文解释公共研究治理和这项历史 Development 研究的身份规范化，不公开私有 manifest、cache、receipt、结果文件位置或哈希，也不推断当前 live 状态。formal-v13…formal-v27 的不可变历史记录仍被保留；规范化只改变解释和未来命名，不重写历史。

状态：Full-Multiscale 经济结论仍是同一个 30 日 historical Development identity 下的阴性结果。BUY 与 SELL 都没有 supported side；没有 final refit、Validation、sealed holdout、action 或 live authority。执行尝试跑完，并不会让研究门槛自动通过。

系列总览见 NarrowGate Full-Multiscale：从多尺度 EMA 到 Boolean Cooldown 的一次阴性研究。项目源码见 NarrowGateMaker。

对 Full-Multiscale，$D$ 是 30 日 family-specific historical Development 与 3,516 个机会；$B$ 是实验冻结时的 exact owner baseline；$C$ 是 B1/B2/B3/E1/E2/E3/M2 加 matched controls；$F$ 是四个 expanding outer folds 及其 nested inner folds；$\theta$ 是 repeated sequential policy 相对 B0 的 campaign-terminal USDC increment；$S$ 则冻结 day/week simultaneous inference、feature hierarchy、tail、lifecycle 与 side-specific gates。

3. formal-v13…formal-v27 为什么容易误导

v13、v14、v15 这样的名字，在普通软件项目中很容易被理解成产品版本；在研究项目中，又很容易被理解成改变了模型或假设的实验版本。如果这些名字实际只是修了 scheduler 或 cache bug，外部读者就无法判断每个版本到底改变了科学问题，还是只让同一个程序更接近可运行。

Full-Multiscale 历史尝试先后遇到 scheduler、cache schema、C++ lockstep、mmap lifetime、resume identity、跨执行 cache binding 和 serialization 一类执行问题。规范化文档因此明确：formal-v13 到 formal-v27 是同一 frozen offline successor identity 下的历史 attempt aliases，不能作为未来把普通修复晋级成 research version 的先例。

未来命名应把两层直接分开：research identity 负责命名科学合同，执行尝试使用 attempt-* 或时间戳；annotated execution tag 再把某次尝试绑定到 exact clean source。名称本身不证明完成，更不证明经济有效。

4. 一条正式执行链需要哪些身份对象

公共治理合同给出的顺序是：

development branch
-> representative single-day output
-> all-fold zero-economic walk
-> concurrency/cache/mmap/resume durability
-> parity and complete-output smoke
-> clean commit
-> annotated execution tag
-> SHA-bound pre-run manifest
-> final receipt or failure receipt

这些对象不是重复记录；它们回答不同问题。

对象 回答的问题 它不能证明什么
Git commit / tree 执行的是哪些 tracked source bytes 外部数据、运行配置、结果或权限
Annotated execution tag 哪个 clean source 被准入这次 attempt 输入齐全、运行完成、经济有效
Pre-run manifest 研究合同、源码、输入、runtime、cache、schema、permission 如何在运行前绑定 最终结果已经生成
Final receipt 哪些完成结果绑定回不可变 manifest 未明确授予的 action/live authority
Failure receipt 尝试在哪里、因为什么失败 部分输出可以继续做经济推断
Artifact SHA256 某个具名 artifact 的精确字节身份 公开可访问位置或科学有效性

Manifest 必须在读取经济结果前冻结，final receipt 只能引用它，不能为了让结果“对上”而回写 manifest。失败也必须留下 receipt；否则团队只会看到最后一次成功，无法知道中间是否发生过会影响选择或缓存语义的问题。

5. 为什么不能把 crash 当成新版本

如果每次程序崩溃都把研究从 v13 升到 v14，会产生三个严重后果。

第一，科学变更与工程修复混在一起。读者看到两个版本时，不知道它们的样本、动作或统计门是否改变，也不知道差异是否只是一个 file descriptor 提前关闭。

第二，失败 attempt 的部分经济输出容易被误用。某一侧或某一 fold 跑完以后，如果下一版直接复用部分 strategy-dependent cache，研究就可能把不同源码、不同运行语义和不同 completion boundary 拼在一起。

第三，版本升级制造了一种虚假的“独立重试”感。同一批 Development 日期没有因为改名而变成新数据；同一个候选也没有因为换了 tag 就获得第二次确认机会。

正确规则是：失败 attempt 的经济推断资格归零，失败记录保留；修复回到 development line，重新通过零经济和 durability gates，再创建新 attempt。只有单独验证的 cache contract 证明 exact semantic identity 时，才可能复用策略依赖缓存；“文件还在”不是充分理由。

6. 一个具体例子：mmap 修复前后

假设 attempt A 的某个进程把 mmap 背后的文件过早关闭，导致后续 worker 在第 18 天崩溃。此前完成的前 17 日输出并不能自动成为最终研究的一部分，因为 completion、resource lifetime 和 aggregate receipt 都没有成立。

修复流程应是：保留 A 的 failure receipt；在普通开发分支修复 resource lifetime；对 BUY/SELL 与所有 backend 跑代表性单日；用 zero-economic preflight 走完所有 outer/inner folds；验证 intended worker count 下的 mmap、并发、atomic cache write、interruption 和 resume；完成 output-shape smoke；然后为 attempt B 建立新的 clean source、tag 与 pre-run manifest。

7. Full-Multiscale 最终是怎样完成组件的

历史上，BUY 组件已在一个不可变尝试中完整 materialize；SELL 则在 runtime 修复并重新完成稳定性门以后独立执行。两侧分别完成四个 outer folds、260 个 OOF candidate-day rows 与 13 张 scorecard，然后只通过 identity-only receipt 组合。

这个 composition 没有 pooled retraining，没有 economic re-estimation，也没有跨执行 strategy-cache reuse。它的作用只是证明两组已完成的 side-specific result 绑定同一个 source、panel、fold、baseline、predicate 与 replay contract。

这是一个历史例外，不是未来模板。未来正式研究应先把完整 executor 稳定到能一次性完成所有 required side 和 backend，再冻结 formal attempt。否则大量 formal-vXX 会把“科学问题是什么”淹没在“程序这次坏在哪里”。

8. 哪些变化真的需要新 research identity

变化 Research identity Execution attempt
修 scheduler、crash、cache atomicity、mmap、resume、serialization 或普通性能问题 保持 重新通过 gates 后创建新 attempt
相同合同下，基础设施失败后重跑 保持 新 manifest、tag 与 receipt
只改公共解释，不改执行和结论 保持 不需要新 attempt
改 30 日样本或替换结果已读日期 新建 新 identity 下的新 attempt
把 B0 换成另一个 baseline，或改变 candidate ladder/duration vocabulary 新建 新 identity 下的新 attempt
改 outer/inner folds、purge 或 embargo 新建 新 identity 下的新 attempt
把 one-shot effect 改成 repeated-policy terminal value，或反向修改 新建 新 identity 下的新 attempt
看见结果后改 primary interval、hierarchy 或 hard gates 新建，而且旧结果必须标记为设计来源 新 identity 下的新 attempt

这张表的核心不是追求更多版本，而是让“什么证据可以互相比较”一眼可见。

9. Identity 和 authority 是两个维度

即使一个 attempt 的 source、manifest、inputs 和 result receipt 全部一致，它也只证明“这次执行可以被精确指认”。它不自动证明 uplift 为正，更不授权 action 或 live。

可以把权限看成另一个独立函数：

而不是 $f(\text{tag 名字看起来多正式})$。Full-Multiscale 的组件执行最终完成，但 day-level uncertainty、hierarchy、tail 与 lifecycle gates 失败，所以研究仍停在 Development，supported_sides=[]。

同理，Git release tag 只标识公共软件发布，research identity 只标识科学合同，attempt tag 只标识一次准入源码，artifact hash 只标识字节。任何一层都不能越权替代另一层。

10. 对 GitHub 读者最重要的阅读规则

看到一个很长的实验目录时，先不要按文件数量统计“研究迭代了多少代”。先比较五项：sample、baseline/candidate、folds、estimand、statistics。如果它们相同，多数差异应归入 execution provenance；如果其中任何一项改变，才是新的研究身份。

然后查看每个 attempt 是否有运行前 manifest、不可变 success/failure receipt，以及明确的 permission fields。一个缺少这些对象的 final 文件名，证据等级可能比一个命名朴素但链条完整的 attempt-* 更低。

最后，保留阴性结果与失败记录。失败 receipt 不是仓库垃圾，而是证明研究者没有悄悄删除不利尝试的 provenance；阴性 Development 结果也不是等待下一个版本号救活的临时状态。

公开证据

  • Formal execution attempt and evidence freeze contract：项目级 research/attempt 分离合同与稳定性门。
  • Source, Research, and Execution Identities：Git source、release、research、attempt、manifest、receipt 与 artifact identity 的公共说明。
  • Execution-attempt normalization：formal-v13…formal-v27 的历史分类与未来命名规则。
  • Formal Development component report：BUY/SELL 分组件完成、identity-only composition 与阴性决定。
  • Executable governance validator：公共代码中的 machine-enforced identity 检查入口。

精确 manifest、cache、result、scorecard 和 receipt bytes 位于 private evidence store，不随公共仓库分发。本文刻意不展示本地路径、运行主机、process id 或裸哈希，因为这些既不是公共读者可访问的证据，也不应被误解为当前 operational authority。
