同一毫秒里谁先发生？订单簿、成交与队列回放的不可识别边界

Last materially modified: 2026-08-29

TL;DR：时间戳相同不等于顺序已知，排个序也不会创造证据

历史订单簿回放经常同时使用 book stream 与 individual trade stream。每条流内部可能有自己的顺序：book delta 有更新序列，trade 有成交 ID；但如果两条流没有共同的跨流 sequence number，而 trade 时间戳只精确到毫秒，就无法知道同一毫秒中的 trade 与 book change 谁先发生。

这不是一个无关紧要的排序细节。队列转移一般不满足交换律：先处理成交再处理盘口变化，可能与先处理盘口变化再处理成交得到不同的 queue ahead、fill、cancel、inventory 与后续 campaign path。用固定的 trade-first、book-first、文件行号或随机抖动做 tie-break，只是制造一个世界，不是恢复真实世界。

NarrowGate 的正确处理是分开证据权限：modeled exchange-time queue 可以作为明确标注且 ambiguity-censored 的 Development 机制证据；strict native identity 在缺少跨流顺序时必须 fail closed；receive/feature-time 证据只回答“策略在决策时已经看见什么”，也不能反向补出交易所撮合顺序。

本文解释公开研究合同中的这个边界。它不读取私有运行状态，也不对当前 live 作任何声明。Full-Multiscale 最终使用的是实验冻结时 exact owner baseline 下的历史 exchange-time、modeled-queue Development identity；30 日、3,516 个机会的研究没有产生 supported side，也没有 final refit、Validation、sealed holdout、action 或 live 权限。

系列总览见 NarrowGate Full-Multiscale：从多尺度 EMA 到 Boolean Cooldown 的一次阴性研究。本文只讨论研究方法和历史证据，不构成任何交易建议。

做一个简化例子。某 maker order 前面估计有 $0.6$ BTC，同一毫秒出现一笔 $0.5$ BTC 的 aggressive trade，以及一个使目标价 displayed quantity 减少 $0.4$ BTC 的 book update。如果 book update 先发生，queue ahead 可能先降到 $0.2$ BTC，随后 trade 有机会越过剩余队列并触及模拟订单；如果 trade 先发生，它先消耗旧队列，后续 book change 的归因与 queue seed 又是另一条路径。具体数值要由冻结的 queue model 决定，但两种处理顺序可能产生“fill”与“not fill”两个不同终点。

一旦第一次 fill 不同，后面就不只差一个局部 label。inventory、cooldown deadline、下一次是否 eligible、订单是否继续留在队列、campaign 何时结束都可能分叉。因此同毫秒歧义会沿着完整路径传播：

3. “不可识别”与“程序跑不动”是两种问题

如果只是程序不知道怎样比较两个对象，可以添加一个任意排序键，让代码继续运行；那是 implementation problem。如果数据本身没有记录真实先后，而两个先后会改变结果，缺少的是 identification，不是算法技巧。

如果两个可行顺序恰好给出同一结果，这个具体机会可能对歧义不敏感；若给出不同结果，严格点标签必须缺失或进入部分识别区间。研究不能因为 missing label 不方便训练，就选择更有利的顺序或填成零差异。

4. Censor 的含义：保留分母，撤回没有证据的点标签

设 $A_i=1$ 表示机会 $i$ 的 active queue/lifecycle path 遇到会改变结果的 unresolved same-millisecond collision，$A_i=0$ 表示没有这种歧义。严格点标签可以写成：

UNIDENTIFIED 不是零 uplift，也不是 baseline outcome。机会仍应保留在 mechanics denominator 与 support report 中，但不能进入需要精确反事实的 point-label learner。若一个机会有八个 duration arms，而冻结合同要求 common support，那么通常需要所有八个 arm 都可识别并共享完整 washout；不能只留下结果好看的几个 arm。

censor 还必须带原因。source gap、queue invalidation、same-millisecond ambiguity、unknown ACK 与 feature unobserved 是不同的证据缺口，后续解释和可支持范围也不同。把它们压成一个 generic missing，会掩盖究竟是状态没看见、订单生命周期不完整，还是跨流顺序根本无法恢复。

5. 三种证据权限不能互相冒充

证据身份 回答的问题 可以支持什么 不能声称什么
Modeled exchange-time queue 在冻结的 exchange-time 事件与明确 queue model 下，动作路径如何变化？ 历史 Development 的机制比较、ambiguity-censored replay、敏感性分析 exact exchange queue、真实 host latency、live 可执行性
Strict native identity 给定原生 book sequence、订单生命周期与可比较的 matching-event order，实际队列路径是否精确可恢复？ 满足全部 source、sequence、lifecycle 与 common-support gate 后的严格历史标签 在缺少 trade/book 共同顺序时继续给点标签
Receive/feature-time identity 某条消息何时到达策略、特征何时 ready、决策时已经可见什么？ causal feature visibility、transport/latency 与可执行性检查 仅凭到达顺序恢复交易所内部撮合顺序，或把历史 exchange time 当成当前 host receive time

modeled queue 不是“错误的 strict queue”，而是问题更窄、权限更低的单独 estimand。它可以帮助判断一个状态—动作机制是否值得继续研究，只要永久标注 model 假设和 ambiguity censoring；它不能因为点估计漂亮就升级为 exact native evidence。

strict native 也不等于“book delta 有 sequence 就够了”。book 的 $U/u/pu$ 一类更新序列只能排序 book stream；individual trade ID 只能排序 trade stream。除非存在共同 matching identity、可证明的 cross-stream mapping，或结果对两种顺序不敏感，否则两套内部顺序无法合成一个精确总序。

这个条件防止策略使用未来信息，却不证明 $e$ 在交易所里先于另一个同毫秒事件。两台系统时钟的绝对值、网络到达先后与撮合引擎顺序是不同概念，必须分别绑定。

6. 哪些 tie-break 看起来合理，却都不能成为 strict evidence

  • 固定 trade-first。它定义了一个可复现模型，但没有证明交易所在所有碰撞中都先处理 trade。
  • 固定 book-first。同样只是另一种模型，不能因为结果更保守或更好看就获得真实性。
  • 使用文件行号或 merge 后的稳定排序。文件排列可能来自下载、分片、序列化或 join 实现，不是跨流 matching sequence。
  • 给同毫秒事件加微小随机 jitter。随机化可以做敏感性分析，却不能识别真实历史路径；不同 seed 也会创造不同经济结果。
  • 把歧义 arm 记为 baseline、zero delta 或 no fill。这样会把未知结果系统性压向某个结论，改变训练 target 与 support。
  • 在歧义以后清零 failure counter 并继续。后续 shared prefix 已经不再 exact，重置计数只会隐藏污染，不能修复状态。

7. NarrowGate 的公开历史给了一个真实反例

早期 strict-native v9 label path 曾尝试一个 41 日 panel。公开 failure report 记录：第一天第一个机会的八个 treatment arm 都在 treatment suffix 遇到 same-millisecond ambiguity，后续 baseline continuation 又累计 queue invalidation 与 ambiguity。最终请求 41 日、admitted day 为 0、admitted panel 为 0，经济结果没有被读取。

这个失败没有证明多尺度 EMA 或 Boolean cooldown 无效；它只证明那份历史数据无法支撑所要求的 strict queue 点标签。项目没有通过重排同毫秒事件“修好”结果，而是关闭该 strict identity，再把可回答的问题转移到一个单独冻结、永久标注的 modeled-queue Development identity。

后来的 Full-Multiscale offline successor 明确采用 modeled_queue_with_same_millisecond_ambiguity_censoring，并把 evidence clock 标成 exchange time。它最终完成 nested OOF，但结论依然只属于该 modeled Development identity：BUY E3 有正点信号但未通过门槛，SELL 无正候选，supported sides 为空。

8. 实践中的最小审计清单

在把 book 与 trade 合并成 queue replay 以前，至少要回答这些问题：

  1. 两条流各自的 timestamp 精度和序列字段是什么？
  2. 是否存在真正共同的 matching identity，而不是同名但不同域的 ID？
  3. 同毫秒碰撞是否会触及 active order 的 queue、fill、cancel 或 lifecycle？
  4. 若交换两种可行顺序，结果是否不变？
  5. 歧义 row 是否保留在 denominator，并以独立 reason censor？
  6. modeled、strict-native 与 receive-time 输出是否使用不同 identity 和权限标签？
  7. feature-ready cutoff 是否保证每个 policy feature 在 decision 前可见？
  8. 报告是否明确写出没有获得的权限，而不只写程序成功完成？

真正可信的回放不要求每行都有答案；它要求“有答案”本身也有证据。遇到不可恢复的顺序，承认不知道通常比提供一个六位小数的伪精确结果更有价值。
